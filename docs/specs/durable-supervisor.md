# Implementation spec: durable supervisor daemon and reduced tool surfaces

**Status:** Accepted — ADR-038 ratified 2026-09-26 on the completed N4.x canary evidence

**Date:** 2026-09-24

**Decision:** [ADR-038](../decisions/038-durable-supervisor.md) (Accepted)

## 1. Objective

Move every piece of supervision state — jobs, supervisors and the Herdr event subscription, the handoff-completion gate, launch intents, and event mailboxes — out of the per-client MCP hosts into one long-lived per-user daemon, so supervision survives client restarts and an interrupted launch becomes safely retryable. Shrink the caller surfaces to three non-Pi MCP tools and five Pi native tools.

## 2. Scope

In scope: the daemon, its socket protocol, durable intent store, filesystem mailboxes, reattach/transfer/claim/reconcile semantics, the reduced MCP and Pi surfaces, and the owner-gated cutover contract.

Out of scope: Herdr core, protocol, or socket changes; activating the systemd unit; changing installed Pi configuration; starting real client cutover. Non-goals: no on-demand or detached daemon spawn, no cursor files, no mailbox rotation, no unread eviction, no MCP cancel or steer, no new dependencies, no auth tokens, no MCP-over-socket, no auto-replay. Devin queue-flush is not scheduled for removal; whether idle-only hints make it dead code is a separate decision after canary evidence.

## 3. Owner-approved contract (binding)

C1. One long-lived **`systemd --user`** herdr-tools daemon per user, thin per-client stdio MCP servers. The unit is committed **inactive** (no `enable`, no `start`); production activation is a separate owner gate.
C2. Non-Pi MCP exposes exactly three tools: **launch**, **ownership/handoff/recovery**, **read-only own-status/unresolved intents**. Status never acks, never moves a cursor, never mutates.
C3. Events live in **per-manager, exact-native-session, owner-only filesystem mailboxes**. Each event is one file with a stable ID and full bounded decision evidence. Read and ack happen through the three-tool MCP surface — reads through the read-only status tool, ack through the run tool; ack is an **atomic rename after handling**. No unread eviction. At capacity the daemon refuses new launches and reports watcher-persistence degradation.
C4. A **verified live owner** may unilaterally transfer its children and unread events to a **verified successor**. Claiming from an **absent** owner requires an owner-instructed policy gate. No pretend same-UID crypto auth. An unresolved launch effect must reconcile before any transfer.
C5. Daemon restart **reattaches** matching live children from a fresh Herdr snapshot, emits a downtime-gap event, and revalidates handoff and review before any completion. It does not blanket-mark runs `recovery_pending`.
C6. When the manager session is gone, **paid reviews pause**; lifecycle watching continues.
C7. Pi exposes exactly five native tools (`bash`, `read`, `edit`, `write`, `ask_user_question`) for **global Pi and all profiles**.
C8. Native follow-ups to children use raw `herdr agent prompt` from the CLI plus an owner-only task-file pointer recipe. No MCP cancel, no MCP steer.
C9. Idle-turn consumption canary for Pi, Claude, Devin **before** disabling Channels or any cutover. A failed leg **stops cutover**; no silent permanent alternate path.

Same-UID routing is cooperative: exact native identity prevents accidental retargeting; it is not an authentication mechanism and the plan adds none.

## 4. Daemon and namespace

- `systemd --user` unit `herdr-tools-daemon.service` (`Type=simple`, `Restart=on-failure`, `HERDR_ENV=1`, `HERDR_SOCKET_PATH` via an owner-written `EnvironmentFile` at activation, `WantedBy=default.target`). Committed only; never enabled or started by this work. Until activation, clients refuse `DAEMON_UNAVAILABLE` — a visible switch, not a drift.
- Endpoint keyed by canonical `HERDR_SOCKET_PATH`: `<dirname(realpath HERDR_SOCKET_PATH)>/herdr-tools-daemon/` holds `daemon.sock`, `daemon.json` (`startedAt`, `heartbeat`, `lastStoppedAt`, capacity state, per-mailbox `unpersisted` loss accounting and `pendingGap` events — §7/§9), `intents/<managerSessionKey>/<key>.json`, `claims/<incidentId>.json` (plus `claims/used/`), `transfers/<transferId>.json` (plus `transfers/done/` — §8), and `mailbox/<managerSessionKey>/{unread,acked}/<eventId>.json`. Mailbox directories 0700, files 0600, owner-only assertion on every open.
- `daemon.sock` is bound only while the namespace lock is held, and an existing path is probed by connect before the bind: an answered socket means a live daemon owns it and startup refuses; `ECONNREFUSED`, or the path vanishing mid-probe, means a stale socket left by a dead process and it is unlinked and rebound; any other error fails startup. Without the probe a crashed daemon leaves `daemon.sock` behind and `Restart=on-failure` loops on `EADDRINUSE` instead of running D4.
- `managerSessionKey` = `sha256(JSON.stringify([source, agent, kind, value]))` of the manager's complete `agent_session`; pane excluded. One key = one native session; a restarted manager agent is a different key, which is why transfer (C4) exists.
- Transport reuses the existing NDJSON framing, correlation, and 256 KiB line bound, plus one bounded version handshake on the same framing: the connecting client's first line is a hello carrying its protocol version and the daemon replies one ack line with its own; a version mismatch gets one bounded `PROTOCOL_MISMATCH` refusal line and the connection closes with no other effect — a fresh client never silently talks to a stale daemon left running by an in-place update. SIGTERM order: flush handoffs → stop supervisors → record `stoppedAt`; no Herdr writes during shutdown. Heartbeat every 30 s.

## 5. Per-request verified identity and project root

**D2a.** Every daemon request carries the thin client's **claimed** identity `{workspaceId, tabId, paneId}` (from its inherited `HERDR_*`), the effective pane plus the `agent_session` it observed by running its own context resolution in its own process, and its canonical project root (realpath'd).

The daemon never reads its own `process.cwd()`, `process.env.HERDR_PANE_ID`, or runs a process-current pane lookup. It takes one fresh `session.snapshot`, requires exactly one pane with the claimed pane ID whose occupant `agent_session` equals the claimed session, and refuses on any mismatch, ambiguity, or unproven claim. The verified project root is written into the intent record and passed to routing/launch as the working directory, so the router decision log, launch cwd resolution, and worktree roots all derive from the caller's root, never the daemon's.

## 6. Durable intents

- **D1.** The intent is recorded before the first effect: temp-write + rename + fsync under a per-manager flock.
- **D2.** The idempotency binding is `(managerSessionKey, idempotencyKey) → (taskDigest, launchId, projectRoot)`. The session key comes from the authoritative snapshot only. `taskDigest` = lowercase-hex `sha256` over the deterministic JSON serialization — object keys sorted recursively, UTF-8, no insignificant whitespace — of the validated Task contract as received: `constraints`/`replicas` normalize to their semantic defaults, while `tier` is digested verbatim — omission lets the workload floor decide, a different contract than an explicit tier — and every field participates, including `tier`, `replicas`, `recoveryOf`, `label`, and `cwd`, so the same key with any field changed is a conflict, never a replay.
- `herdr_launch` gains a required `idempotencyKey` (1–128 chars, `^[A-Za-z0-9._:-]+$`); the rest of the Task contract, including `recoveryOf`, is unchanged.
- Lifecycle: `recorded` (fsynced, no effect yet) → `effecting` (written immediately before the first durable or child mutation) → `completed | failed`. `failed` is reachable only with evidence that no child effect exists — a pre-effect failure or a confirmed cancellation; any post-effect result with `partial` or `unknown` effect certainty is `unresolved`, never `failed`, and the launch result preserves the launcher's effect certainty (`absent | partial | unknown | confirmed`) through the error projection so the daemon classifies on it rather than dropping it. An interrupted effect likewise becomes `unresolved`, never auto-replayed.
- Replay requires the same key, digest, session, and verified project root — the `projectRoot` in the D2 binding must equal the request's canonical root exactly, never silently substituted for the caller's: still `recorded` (the previous attempt died pre-effect) → the launch **resumes** under the same minted `launchId`; `effecting`, `completed`, or `failed` → the recorded state is returned with `replayed:false` and zero effect; `unresolved` → returned with recorded child names and run IDs — the caller runs `reconcile` — which closes the intent once every recorded child is classified (§8) — then `recoveryOf` or a new key. A different digest or a different project root under the same key and session → `IDEMPOTENCY_KEY_CONFLICT`. A different session under the same textual key selects a different `(managerSessionKey, key)` binding — a separate intent record, not a conflict — and proceeds as that session's own launch; keys are scoped per native session, no global key index exists, and no cross-session conflict is fabricated.
- **D3.** Crash windows: before the `recorded` fsync there is no intent and a fresh launch proceeds; between `recorded` and `effecting` the launch resumes with the same `launchId`; after `effecting` a restart surfaces `unresolved`. `unresolved` blocks transfer and claim until `reconcile`.

## 7. Mailboxes

- Path: `mailbox/<managerSessionKey>/unread/<eventId>.json` and `acked/<eventId>.json`. `eventId` = `<ISO-8601 UTC timestamp, ms, colons removed>-<randomUUID>` — sortable by time, no durable counter. `runId`, `jobId`, `kind` live in the body, not the name.
- No-clobber write: write the body to a temp name in the same directory, fsync the file, `link(temp, final)` — which fails `EEXIST` rather than silently replacing — then unlink the temp and fsync the directory. A collision is refused, never overwritten, and reported as `persistenceFailed`. Every event write resolves its destination mailbox from the run's **current** owner — never the owner recorded at supervisor bind — and completes while holding the run flock, performing the capacity check and the `link` under the fixed flock order — the short global mailbox-index flock first, then the destination mailbox flock — with the per-manager file/byte counts and the global `unread/` count recomputed under them at write time — the same mailbox flock `transfer` holds: a write that lands before the freeze is moved with it, a writer blocked mid-transfer lands in the successor's mailbox on release, and the capacity bound is atomic with the write.
- Body, bounded ≤ 32 KiB: run-scoped events carry `{id, at, kind, runId, jobId, childIdentity, decision:{verdict, labels, evidenceDigest, evidenceExcerpt≤8KiB, reviewerModel|"paused"}, handoff:{state, artifactSha256}, actions:[...]}`; mailbox-global events carry `{id, at, kind, ...}` with their own payload — `downtime_gap` is `{id, at, kind, from, to, lost}` with no `runId`/`jobId` — full bounded decision evidence so the manager can act without a second call.
- Mailbox access rides the three-tool surface — no separate helper: `herdr_status` is the read projection — the unread ID list always, plus the bounded event body when the caller names an event ID; `herdr_run` carries `ack` — rename `unread/` → `acked/` **after** handling; idempotent; each ack then prunes `acked/` to the newest 1 000 files by eventId order — timestamp-prefixed names make oldest-first a plain name sort — and `acked/` files are handled records, so pruning them is not unread eviction and the no-rotation non-goal stands for unhandled events.
- Capacity is a hard bound on event writes, not eviction: per-manager `unread/` cap 500 files or 8 MiB; global cap 5 000 `unread/` files summed across all mailboxes (`acked/` counts toward neither cap — it is bounded separately by the 1 000-record retention above) — both counts recomputed at write time under a fixed flock order: the short global mailbox-index flock first, then the destination mailbox flock (every taker of more than one mailbox flock — `transfer`, `claim` — acquires them in `managerSessionKey` order after the index flock), so global admission is atomic with the `link` and racing writers cannot overshoot. Files moved by `transfer`/`claim` are not exempt: the journaled move always completes rather than being refused or split, and moved files count toward the destination's caps, so a mailbox pushed over cap refuses later writes until it drains. The one residual overshoot is stated, not hidden: a journaled move can carry a mailbox over cap — the caps bound new writes, never strand a journaled transfer. At cap: no eviction, no spool; `daemon.json.capacity="degraded"`; new `herdr_launch` refused `MAILBOX_CAPACITY` with no child effect; supervision of existing children continues. An event that cannot be written is never claimed as persisted: the supervisor keeps it in memory only, records `persistenceFailed:true` with the event ID on its job view, `herdr_status` reports `watcher_persistence_degraded` with the unpersisted count, and the daemon records the loss durably — `daemon.json.unpersisted[<managerSessionKey>] = {count, firstAt, lastAt}`, rewritten atomically on each failed persist, so the accounting survives the daemon stop the payloads do not. A mailbox event that cannot be written because the mailbox is still at cap — including the `downtime_gap` that must disclose that loss — is held as `daemon.json.pendingGap[<managerSessionKey>]`, retried after room (rechecked on every heartbeat while pending), and reported by `herdr_status` until it lands; the record clears only when the event is durably written. Bounds, stated not absorbed: payloads refused at cap are unrecoverable; a pending gap is guaranteed delivery only once the mailbox has room; a mailbox that never frees keeps its loss record in `daemon.json` and in status output — disclosure degrades, it is never destroyed; and if the `daemon.json` write itself fails, nothing claims persistence and the failure is logged. The `unpersisted` accounting bound covers an event once its persist attempt fails; a crash between the failed persist and the `daemon.json` rewrite is outside it.

## 8. Ownership: observe, reconcile, transfer, claim

`herdr_run` carries five operations. Names are review proposals; the owner contract fixes semantics, not names.

- `observe` (read-only): the `resumeHandoff` result, intent state, and unread event IDs for the run.
- `reconcile`: for an `unresolved` intent, re-reads a fresh snapshot and the v2 sidecars of every recorded run, and classifies **every** recorded child identity — one intent can carry a Task's full replica set (1–8 children). Each child: live and matched → bind supervision; provably absent → `identity_lost` with the snapshot evidence recorded; ambiguous → recorded with evidence. The intent moves to `completed(reconciled)` once every recorded child is classified — live-bound or provably absent (`identity_lost`) — with zero ambiguous, the per-child dispositions recorded in the intent so the reconciled result still discloses which replicas were lost; any ambiguous replica leaves the intent `unresolved` with the dispositions recorded, so no partial classification clears the gate while a replica is unaccounted. A provably absent child therefore resolves rather than strands the intent: transfer and claim vetoes then concern only effect-uncertain or ambiguous intents, permanent absence cannot strand ownership, and the caller replaces lost work through `recoveryOf` or a new key on the closed intent. Never launches, never prompts, never fabricates a terminal state.
- `transfer` (live owner → successor): the caller must be the **verified live owner** — a fresh snapshot proves the caller pane's `agent_session` equals the recorded owner. Input: successor pane ID. The daemon proves the successor has a complete `agent_session` and a supported kind, and refuses while any owner intent is `unresolved`. It then runs the transfer as a **journaled sequence of idempotent steps**: under the run flock it first writes a durable `transfers/<transferId>.json` record — the same temp+rename+fsync primitive as D1 — freezing the plan: the runs, both session keys, the provenance v2 owner entry per run, the owner's complete `unread/` filename set to move — every unread event the owner holds, run-scoped and mailbox-global alike — and the minted IDs and bodies of the two `transfer` events. Then under run + mailbox flocks it rewrites `provenance.json` as **v2** — `owners: [{session, from, to|null, reason}]` with the original manager as the first entry; every reader accepts v1 and v2, resolves the current owner as the last open entry, and reads v1 as single-owner history; no arbitrary key is appended to a v1 record — renames every file in the owner's `unread/` into the successor's `unread/`, fsyncing both mailbox directories after each rename (a file already absent from the source counts as moved only when the destination file exists; a file absent from both goes to the durable §7 loss accounting, never silently skipped; moved files count toward the successor's §7 caps — the journaled move always completes rather than being refused or split on capacity, and an over-cap successor refuses later writes until it drains), appends the two recorded `transfer` events through the §7 no-clobber write (an existing event ID means already written), re-targets supervisor hint destinations, and marks the record done under `transfers/done/`. A restart completes any record not marked done before serving ownership operations on those runs (§9). The record is the minimal crash-recovery state, and a smaller shape fails: no ordering of the provenance rewrite, file moves, and event pair survives a crash between them, a retry without the frozen plan would mint fresh event IDs and duplicate the mailbox events, and nothing else distinguishes a finished transfer from one interrupted mid-commit.
- `claim` (absent owner → caller): only when (a) no pane in the fresh snapshot carries the recorded owner session, (b) no `unresolved` intents exist on the named runs, and (c) a per-incident owner-instruction record `claims/<incidentId>.json` exists and matches exactly: `{priorOwnerSession:{source,agent,kind,value}, successorSession:{source,agent,kind,value}, runIds:[...], instructedAt, instruction:"<owner text>"}`. The caller's fresh `agent_session` must equal `successorSession`, each run's recorded owner must equal `priorOwnerSession`, and the requested run set must equal the record's `runIds` exactly — a subset, a superset, or any other difference → `CLAIM_NOT_INSTRUCTED`. On success the claim performs the identical journaled sequence as `transfer` — the `transfers/<transferId>.json` record freezes the same plan and additionally carries the `incidentId`, the provenance v2 rewrite, unread moves, recorded event pair, supervisor retarget, `transfers/done/` completion, and the same D4 restart completion apply — with the validated record's rename to `claims/used/` as a journaled step ordered before the mutations, so it cannot authorize a second claim, restart completion never needs the record, and a record left unconsumed by a crash is refused afterward because the recorded owner no longer equals `priorOwnerSession`. No global allow-file exists. This is a cooperative gate; same UID is not authority.
- `ack` (mailbox): renames `unread/<eventId>.json` → `acked/<eventId>.json` in the caller's own mailbox — resolved from the verified session; no argument names a session — **after** the caller has handled the event; the C3 atomic rename, idempotent — an already-acked ID is a success no-op; each ack prunes `acked/` to the newest 1 000 records (§7).

No `cancel`, no `steer` (C8).

## 9. Restart, absence, and downtime

- **D4 restart:** acquire the namespace lock → probe and bind `daemon.sock` per §4 (live owner → refuse to start; stale path → unlink and rebind) → load intents, pending `transfers/` records, and v2 run sidecars → complete every transfer not marked done → take a fresh `session.snapshot` → for each recorded child identity of each run in `awaiting_handoff` **or `recovery_pending`** — a run a prior host (or an earlier daemon start) left `recovery_pending` is re-matched by the same rule, never silently skipped: a pane matching terminal, name, kind, and session → **reattach** (reserve and bind a supervisor for that exact identity; revalidate the `handoff.md` digest and the last review record before any completion event); child provably absent from the snapshot → `unresolved(identity_lost)` with the sidecar preserved untouched and the gap recorded; ambiguous match → `recovery_pending` with evidence — a run already in `recovery_pending` stays there, and this is the only restart path into that state. The daemon never writes `failed` or any completion for a result it did not observe. Then one `downtime_gap` event `{from: lastHeartbeat, to: startedAt, lost}` to every affected mailbox — `lost` carrying the durable `unpersisted` accounting per §7; a mailbox still at cap takes the event as `pendingGap`, retried after room, so the disclosure is deferred, never dropped.
- **D5 absent owner:** the owner session missing from the snapshot → `reviews:"paused"` — no reviewer calls — while lifecycle watching continues and lifecycle events keep landing in the unowned mailbox; reviews resume on `transfer` or `claim`, and resume automatically when the recorded owner session reappears in a fresh snapshot — a transient absence (pane move, reconnect, snapshot race) pauses reviews, it does not strand them.
- **D6:** every response is bounded (`MCP_RESULT_MAX_BYTES`; the 256 KiB wire line bound).

## 10. Surfaces

- **Non-Pi MCP — exactly three tools, the universal harness surface.** `herdr_launch` (§6), `herdr_run` (§8 — including mailbox `ack`), `herdr_status` — read-only: daemon health and latest gap event, the caller's runs (lifecycle, child presence, review `active|paused`), the caller's intents (`unresolved` first), unread event count and IDs, the bounded event body when the caller names an event ID (the mailbox list/read projection, §7), mailbox path, capacity state. Status opens nothing for writing, never acks, never mutates. Every harness reaches the same three tools: Claude and Devin natively over MCP, Pi through the executor MCP gateway — executor→MCP is the only daemon-access path; there is no CLI surface. `herdr_communicate`, `herdr_wait`, `herdr_jobs`, `herdr_pane`, `herdr_tab`, and `herdr_inspect` leave the caller surface; internals remain daemon library code where launch and supervision need them.
- **Pi — exactly five native tools.** The extension registers nothing; `read`, `bash`, `edit`, `write`, `ask_user_question` for global Pi and every profile lane — the C7 set is unchanged. Only the daemon-access path changed: Pi reaches the same three tools through the executor MCP gateway, not a shell command.
- **Native follow-ups (C8).** Manager → child text uses the installed CLI signature exactly: `herdr agent prompt <TARGET> <TEXT>` (positional; no stdin or file flag). Large content never travels in argv: the manager writes an owner-only file `herdr-handoffs/<runId>/followups/<seq>.md` (0600) and `<TEXT>` is one short pointer line, e.g. `herdr follow-up <runId>/followups/<seq>.md`; the child reads the file with its own `read` tool. No daemon involvement, no MCP tool. The raw send bypasses the package's write lock and composer flush (ADR-029), and a prompt sent to a busy Devin pane can sit in the composer queue past the turn's end (ADR-027) — so for a `devin`-kind child the recipe sends only to a freshly verified `idle`/`done` pane: the manager re-reads the pane immediately before the send and defers, never sends, while the state is `working`, `blocked`, unknown, or unproven. The check is fresh, not atomic with the send; the residual race window is stated, not hidden. Non-Devin kinds are unchanged — Pi steers the same write into the running turn.

## 11. Idle hints and the consumption canary

- Hints are best-effort only: after writing an event, a fresh `pane get` on the owner pane; if `idle` or `done` and the kind is in the qualified set, one `agent.prompt` with body `herdr mailbox: <n> unread (<ids…>) at <path>; read via your MCP surface (herdr_status / executor → MCP)`, coalesced per manager per 5 s. Busy, unknown, unproven, unsupported (agy), or non-qualified kinds get nothing — the mailbox is the durable path. This idle-only gate is a deliberate deviation from ADR-027's no-busy-gate wake, recorded in the ADR. **Recorded caveat (C9 canary, kept visible):** a Devin pane today exposes the legacy `herdr_*` MCP names, not `herdr_status` — the Devin canary leg still consumed the hint by reading the mailbox files directly. The body names the post-cutover surface; the body text and Devin's actual surface are reconciled at the N5.3 owner cutover — the direct-registration removal diffs move Devin onto the same three tools through the executor gateway — not before, while still-live Devin managers keep the legacy surface.
- The production qualified-kind set defaults to **empty**. The C9 canary has now passed for all three kinds — Pi, Claude, Devin — each proving the pane consumes the hint as a turn (per-kind evidence recorded in ADR-038's canary table, including the AGY-inert, busy-owner, coalescing, and stock-daemon legs); a failed leg would have stopped cutover outright — no Channels disable, no silent permanent alternate path (C9). Enablement is a code flip, not a configuration knob: the production daemon entry passes `hintKinds` naming the qualified kinds (`pi`, `claude`, `devin`) only when N5.2 lands, in the same change that removes the Channels branch and capability; the disposable test daemon remains the only other place a non-empty set may be injected (`HERDR_TOOLS_DISPOSABLE_HINT_KINDS`). Until the flip lands, the shipped default stays empty and hints are inert — the mailbox is the durable path either way. The Devin leg additionally covered the C8 path itself: a raw `herdr agent prompt` follow-up sent to a verified-idle Devin pane was observed consumed as a turn, never left queued in the composer — the mailbox-hint canary did not substitute for the follow-up recipe.

## 12. Removals gated by this spec

Each removal is its own gated step; none lands before its gate: the Pi extension tool registration and the Pi-host runtime copy (C7); the client-side sequential tool queue (the daemon serializes); the seven-tool MCP surface down to three; the Channels wake path and capability — only after all three C9 legs pass; hardcoded host paths → the daemon namespace; `scripts/resume-handoff.mjs` folded into `herdr_run observe`. The seven-tool surface removal carries a skill-migration gate over every shipped skill text, not only manager skills: the canonical `herdr-profiles/role-plugins/manager/skills/{manager,harness-flow}`, every other shipped role skill whose text prescribes a removed tool, their generated profile-plugin copies, and bundle pins are migrated first to the reduced surface and its recipes (the three tools — reached through the executor MCP gateway from Pi — mailbox read→act→ack via `herdr_status`/`herdr_run`, the idle-gated follow-up recipe, `idempotencyKey`), so no shipped skill text still prescribes a removed tool or forbids the prescribed executor→MCP path; the removal step is refused while any shipped skill text does. The `herdr-manager` skill's canonical source lives outside this repository (its bundle pin records it); its recipe update is **prepared, not landed**, in this gate — landing it at that source and refreshing the pin is an ordered step of the owner cutover, so no external repository is mutated before activation and still-live managers never receive a recipe for a surface that does not yet exist — migrated, not silently skipped.
